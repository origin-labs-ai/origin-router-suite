# v0.5.116 — Docker LAN gate + Windows release disk

The v0.5.116 cut that failed in CI, re-cut with the two failures fixed. Both were
found by reading the failed run logs, not by guessing.

## Fixes

### The Docker image answered 403 to its own host

`docker-push` failed on both architectures with `curl http://127.0.0.1:20128/api/health`
→ **403 `LAN access is disabled.`**

The cause was not CI. Inside a container, the host's own traffic to a published
port is NAT-ed to the container's **default gateway** (`172.17.0.1` on the default
bridge). `custom-server.js` stamps that address as the real peer IP, and the LAN
gate then read it as "a private network device that is not this computer" — so
the image refused *everything* the host sent it: the dashboard, `/v1`, and its own
health check. A `docker run -p 20128:20128` install was unusable until the
dashboard could be opened, and the dashboard could not be opened.

The fix keeps the gate exactly as strict for everyone else: a new
`src/lib/containerNetwork.js` reads the container's default route from
`/proc/net/route`, and that one address — the machine that published the port —
counts as "this computer". A device on the LAN keeps its real IP and is still
blocked unless **Allow access from this network** is switched on. The lookup only
runs when the image sets `OR_CONTAINER=1`, because on a native Linux host the
default gateway is the router, and treating the router as local would hand the
dashboard to the whole network.

Covered by `tests/unit/container-network.test.js` (7 cases: the gate is off
outside a container, off on a non-Linux host, the default route is parsed
correctly, the gateway counts as local, a missing route table is not a gateway).

### The Windows release ran out of disk

`release` failed after 1h47m with `ENOSPC: no space left on device` while
packaging the portable folder. The work tree lives on the runner's `D:` drive,
which starts with ~14 GB free, and the job was carrying three copies of the same
app: a **redundant root `npm run build`**, the CLI build's own `.next-cli-build`
tree, and the root `node_modules` — none of which ship. The installer only ever
packages `cli/app` → `dist/win`.

The Windows job now builds the CLI bundle once (that build runs Next.js itself
and fires the root `postbuild` hook), then removes `.next`, `.next-cli-build` and
the root `node_modules` before packaging — ~3.2 GB back, and about 20 minutes
faster. The job prints free space at that point so the next disk failure is
diagnosable instead of silent.

### Release notes are part of the release

`release.yml` now picks up curated notes from `docs/releases/<tag>.md` when they
exist and falls back to the generated changelog when they do not, so a release
never ships with an empty description.

## Changed

- Nothing user-facing. The behaviour of the LAN gate is unchanged for anyone
  running the app directly on Windows or macOS: loopback is local, the LAN is
  opt-in.
